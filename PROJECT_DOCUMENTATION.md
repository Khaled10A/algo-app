## 1. Project Overview

**Algo App** (`package.json` → `"name": "algo-app"`) is a client-side React single-page application for **visualizing, benchmarking, and step-by-step debugging** of classic computer-science algorithms. It was built as the companion tool for a **Design & Analysis of Algorithms (DAA)** course, and is deployed live at `https://algo-app-lilac.vercel.app` (per `README.md`).

The product is organized into **three top-level domains** (`src/algorithms/registry.js`, `DOMAINS`):

| Domain | Label | Available sub-tabs |
|---|---|---|
| `sorting` | Sorting | benchmark, visualizer, complexity, pseudocode, history, report, debugger, ai |
| `searching` | String Matching | benchmark, complexity, pseudocode, history, report, debugger, ai (no visualizer) |
| `graphs` | Graphs | debugger (a full interactive graph playground) |

Inside each domain the app provides benchmarking with charts and tables, an animated array visualizer, a memory debugger with code highlighting, a Big-O complexity reference, pseudocode panels, run history, auto-generated report text, CSV/XLSX/PNG exports, and an AI tutor chat (Arabic/English) whose requests are proxied through a serverless function.

The repository is small and dependency-light: React 18 + Vite 5, hand-written SVG charts (no chart library), no routing library, no UI component library, no external algorithm library, and no database. One serverless endpoint (`api/assistant.js`) proxies chat completions to Groq so that the model-provider API key never ships to the browser.

## 2. Purpose and Problem Being Solved

The app exists to support learning/teaching the **Design and Analysis of Algorithms**. It solves a set of problems that students of a DAA course typically face:

- **Empirical verification of theoretical complexity.** The Benchmark tab measures real wall-clock time (median of repeats after JIT warm-up) and basic-operation counts (comparisons) for algorithms over controlled input shapes (random / sorted / reverse / nearly sorted arrays; text scenarios with pattern at start, end, multiple occurrences, or absent), then visualizes them on line/bar charts and cross-checks measured growth against the stated Big-O formula (`src/tabs/ReportTab.jsx`).
- **Understanding execution, not just output.** The Debugger and Visualizer turn algorithms into replayable step streams with animated array bars, variable watches, memory tables, call stacks, per-line source highlighting, priority-queue/queue/frontier state, and distance matrices.
- **Fair comparisons.** Benchmarks share identical generated inputs across all selected algorithms, aggregate repeated timing with the median, and run inside a Web Worker so the UI never freezes (`src/core/benchmark/engine.js`, `runner.js`).
- **Study of multiple algorithm families.** The same canonical descriptor format covers sorting (8), string matching (3 benchmarkable + Binary Search debugger), and graph algorithms (DFS, BFS, Dijkstra, Bellman-Ford, Floyd-Warshall, Prim, Kruskal) with pseudocode and complexity metadata for each.
- **Keeping the model API key out of the client.** The AI Assistant only ever calls `/api/assistant` (or `VITE_AI_ENDPOINT`); the Groq key is read server-side from `GROQ_API_KEY` (`api/assistant.js`, `README.md`).

## 3. Main Features

1. **Sorting benchmark** — select any of the 8 sorting algorithms, 4 input shapes, comma-separated input sizes, metric (time or comparisons), custom arrays, run/cancel; results render as line/bar charts plus per-type tables with best/worst performer callouts (`src/tabs/BenchmarkTab.jsx`, `src/App.jsx`).
2. **String matching benchmark** — Brute Force, Horspool, KMP over generated text (start / end / multiple / no-match scenarios) or an uploaded `.txt` file, with match counting and per-algorithm ranking in file mode (`src/tabs/BenchmarkTab.jsx`).
3. **Visualizer** — animated vertical bar arrays with swap/compare highlighting, per-bar value/index labels, sorted-region & heap-boundary markers, comparison counters, audio tones, speed presets, scrubbing, step controls, replay (`src/tabs/VisualizerTab.jsx`). Only sorting algorithms that expose a `steps` generator are visualizable (Insertion, Bubble, Selection, Heap, Counting, Radix).
4. **Memory debugger** — step-by-step execution of all 8 sorting algorithms, Binary Search (found/not-found), and the 3 string matchers, with live arrays/bars, string grids, LPS/shift tables, variables, memory snapshot, call stack and line highlighting, plus text/file input modes and truncation safeguards (`src/tabs/DebuggerTab.jsx`).
5. **Graph playground / debugger** — an interactive SVG graph editor (place/connect/delete nodes & edges, set weights, click-to-edit) combined with step debuggers for DFS, BFS, Dijkstra, Bellman-Ford, Floyd-Warshall, Prim and Kruskal: colored visit states, queues/heaps/frontier panels, distance badges per node, predecessor trees, matrix view, negative-cycle alerts, MST/forest summary (`src/components/visualizer/GraphDebugger.jsx`).
6. **Complexity reference** — best/average/worst/space/paradigm table plus a "run side-by-side (n=100)" comparison (`src/tabs/ComplexityTab.jsx`).
7. **Pseudocode** — canonical pseudocode + complexity chips for every registered algorithm (`src/tabs/PseudocodeTab.jsx`).
8. **Run history** — up to 20 persisted past runs with select-up-to-4 side-by-side comparison tables and mini-bars (`src/tabs/HistoryTab.jsx`, `src/hooks/useRunHistory.js`).
9. **Auto report** — narrative analysis of the last benchmark (best/worst algorithm, per-type winners, measured-vs-theoretical scaling) ready to copy into coursework (`src/tabs/ReportTab.jsx`).
10. **Exports** — CSV, Excel `.xlsx` (SheetJS, with automatic CSV fallback), and PNG export of all four charts (`src/utils/exportUtils.js`).
11. **AI Assistant** — Arabic/English chat with per-language system prompts, quick actions, an "analyze results" mode that feeds actual benchmark numbers to the model, and an algorithm-recommender form; proxied via `api/assistant.js` (`src/tabs/AIAssistantTab.jsx`).
12. **Persistence** — dark/light theme, selected options, latest results and run history survive reload via `localStorage` under the `algo-app:v1:` prefix (`src/hooks/usePersistentState.js`).
13. **Polish/a11y** — Liquid-Glass-style theme system with dark & light palettes (`src/theme/tokens.js`, `src/styles/index.css`), keyboard-accessible radio groups with arrow keys, `aria` labels, focus-visible rings, reduced-motion support, and an app-wide error boundary.

## 6. Complete Project Architecture

Algo App follows a **descriptor-driven, three-tier architecture** designed so that adding one algorithm requires touching only the algorithm folder + the central registry (`README.md` "Architecture"; `src/algorithms/registry.js`):

```
┌────────────────────────────────────────────────────────────────────┐
│ TIER 1 — ALGORITHM CORE (pure JS, no UI)                            │
│   src/algorithms/{sorting,searching,graphs}/*.js                    │
│   • run()  → { sorted/matches/distances/..., comparisons }          │
│   • *Events(input) → deterministic event stream (heap/counting/     │
│     radix, dijkstra, bellman-ford, floyd-warshall, prim, kruskal)   │
│   • *Debug(input)  → step snapshots for the debugger                │
│   • *Steps(input)  → frames for the visualizer                      │
│   • descriptors.js → canonical descriptor objects                   │
│   src/core/structures (MinHeap, DisjointSet),                       │
│   src/core/execution/events.js (createEventCollector)               │
└───────────────┬────────────────────────────────────────────────────┘
                │ registered in
                ▼
┌────────────────────────────────────────────────────────────────────┐
│ TIER 2 — REGISTRY + PROJECTORS                                      │
│   src/algorithms/registry.js — ALL_DESCRIPTORS, DOMAINS, lookups    │
│   Projectors map algorithm event streams → UI snapshots:            │
│     sorting/sortingSteps.js · graphs/pathfindingSteps.js            │
│     graphs/mstSteps.js · graphs/floydWarshallSteps.js               │
│   Benchmark: jobs.js → engine.js, run inside worker.js (with a     │
│   main-thread fallback for small jobs)                              │
└───────────────┬────────────────────────────────────────────────────┘
                │ state flows through hooks
                ▼
┌────────────────────────────────────────────────────────────────────┐
│ TIER 3 — REACT UI                                                    │
│   src/App.jsx — navigation model + all persistent settings           │
│   hooks/ — useBenchmarks · usePlayback · usePersistentState ·       │
│            useRunHistory                                             │
│   components/ — Header, ConfigSidebar, charts (SVG), Shared UI,     │
│                 GraphDebugger + MatrixView, ErrorBoundary            │
│   tabs/ — Benchmark, Visualizer, Debugger, Complexity, Pseudocode,  │
│           History, Report, AIAssistant                               │
│   theme/ + styles/ — tokens, ThemeContext, index.css                 │
│   utils/ — generators, constants, exportUtils, audio                 │
└────────────────────────────────────────────────────────────────────┘
                │ optional backend call
                ▼
   api/assistant.js — serverless Groq proxy (GROQ_API_KEY server-side)
```

Key architectural ideas, all verifiable in code:

1. **Algorithms are described once.** `src/algorithms/registry.js` flattens `sortingDescriptors`, `searchingDescriptors`, `graphDescriptors` into `ALL_DESCRIPTORS` and indexes them by id. A descriptor carries `{ id, name, category, group?, color, complexity, run?, steps?, debug?, pseudocode, codeLines }`. Lookups never throw in render paths (`getAlgorithmSafe`, `getAlgorithmForDisplay` in `registry.js`) so stale persisted ids degrade gracefully (covered by an E2E test, `cypress/e2e/app.cy.js`).
2. **Event-execution + projector seam.** Graph algorithms (Dijkstra/Bellman-Ford/Floyd-Warshall/Prim/Kruskal) and the three "modern" sorts (Heap/Counting/Radix) do not generate UI snapshots directly. They run through `createEventCollector()` (`src/core/execution/events.js`) producing a deterministic, JSON-serializable event list; a projector — `src/algorithms/sorting/sortingSteps.js` (sorts) and `src/algorithms/graphs/pathfindingSteps.js` / `mstSteps.js` / `floydWarshallSteps.js` (graphs) — maps each event to exactly one debugger/visualizer snapshot. Tests assert *one event → one step* and full determinism (e.g. `src/algorithms/graphs/dijkstra.test.js`).
3. **Benchmark as a job graph.** `src/core/benchmark/jobs.js` validates and *materializes* a plain spec into `{ algos, scenarios, sizes, repeats, warmup }`; `engine.js` runs it sharing one prepared input per (scenario, size) across algorithms; `runner.js` executes it in a Web Worker (`worker.js`) with AbortSignal cancellation, a 2-minute watchdog, typed errors, and a synchronous fallback for small jobs.
4. **Stateless React shell.** `App.jsx` holds all settings via `usePersistentState` and passes plain "control" objects down into `ConfigSidebar`/tabs; there is no global store.
5. **No server database** — persistence is browser `localStorage` only (see §11).

## 8. Application Flow

### Boot
1. Browser loads `index.html` → `src/main.jsx` mounts the app inside `StrictMode` + `ErrorBoundary`.
2. `App.jsx` reads persisted state from `localStorage` (`usePersistentState`): theme (default dark), domain (default `sorting`), sub-tab (default `benchmark`), and all domain settings. It validates the persisted sub-tab against the domain's `subTabs` and falls back to the first one (`App.jsx`).
3. `document.body.dataset.theme` is set; the `ThemeCtx.Provider` wraps the layout; `Header` + (optionally) `ConfigSidebar` + `<main>` render.

### Benchmark flow (sorting and string matching)
1. User configures algorithms, input type/shape/scenario, sizes/pattern/custom array, metric, mode in `ConfigSidebar`.
2. Clicking RUN invokes `handleRunSort`/`handleRunSearch` in `App.jsx`, which call `runSort`/`runSearch` (`src/hooks/useBenchmarks.js`).
3. The hook builds a plain **spec** object, runs `validateSpec` (`src/core/benchmark/jobs.js`); on validation failure an error string is surfaced in the sidebar (`BenchmarkError`). Otherwise an `AbortController` is created and `runBenchmark(spec, { signal })` is called (`src/core/benchmark/runner.js`).
4. The runner posts the spec to `worker.js`; the worker calls `executeSpec` → `materializeSpec` → `runBenchmarkJob` (`engine.js`): per (scenario, size) an input is generated *once*, then each algorithm is measured with warmup + repeats (defaults 1 warmup, 5 repeats — `DEFAULT_REPEATS`/`DEFAULT_WARMUP` in `jobs.js`), aggregating the median time and counting comparisons. A `{ok:true, results}` message returns.
5. `useBenchmarks` wraps results into a run **envelope** `{id, kind, label, ts, metric, results, sizes, algos, types|scenarios, inputMode, customArr?, mode?, fileName?, …}`, stores it as persisted "latest result", and returns it; `App.jsx` appends it to run history (`useRunHistory`, max 20).
6. `BenchmarkTab` renders `SortResults`/`SearchResults`: worst/best performer cards, line & bar charts, and per-type/scenario data tables. Both the sorting and the string-matching tables emit one cell per input size plus the trailing "Basic Ops" (comparisons at the last size point) and "Theoretical Formula" (descriptor worst-case string, with a numeric ≈ estimate only when the formula is numeric) columns — identical logic in `SortResults` and `SearchResults` (`src/tabs/BenchmarkTab.jsx`). In file mode the charts and scenario tables are replaced by a file-info card, a ranked table with match counts, and per-algorithm comparison bars.
7. Export buttons call `exportCSV`/`exportXLSX`/`exportAllChartsPNG` (`App.jsx` → `src/utils/exportUtils.js`); chart cards offer per-chart PNG and fullscreen.

**Concrete example — one sorting run, end to end.** Field names and nesting below match exactly what `useBenchmarks.js` produces; only the numbers are illustrative. Selecting `insertion-sort` + `merge-sort`, sizes `"1000, 5000"`, shapes Random + Sorted, metric Time, then clicking RUN yields:

### Visualizer flow (sorting)
1. User picks algorithm + size; App's `startViz()` calls `descriptor.steps(generateArray(size, "random"))` producing frames `[{arr, highlight, …}]` (`App.jsx`), stores them in state, and resets `usePlayback`.
2. `VisualizerTab` renders bars from `steps[playback.index]`, drives playback with RAF, plays audio per highlighted step, and computes ops-done counters.

### Debugger flow (sorting/searching/graphs)
1. `DebuggerTab` (`src/tabs/DebuggerTab.jsx`) or `GraphDebugger` calls the selected algorithm's `debug(...)` function to produce snapshots, then steps through them with `usePlayback`.
2. Snapshots share a schema `{activeLine, log, vars, memory, callStack, …}` plus domain extras (`arr/highlight`; `text/pattern/highlightText/highlightPat/matchPositions/lpsTable/shiftTable`; `visited/queue/heap/distances/previous/matrix/frontier/mstEdges/…`).
3. Inputs are capped and truncated with visible notices (max debug array 64, text 2000 chars, pattern 100 chars — constants exported from `DebuggerTab.jsx`).

### Report / History / Pseudocode / Complexity / AI flows
- **Report** (`ReportTab`) reads the latest sort/search result envelopes and composes narrative text; if neither exists it shows an empty state.
- **History** lists past runs; selecting runs (≤4, same kind) shows comparison tables with bars.
- **Pseudocode** renders `descriptor.pseudocode` + complexity chips for the selected algorithm.
- **Complexity** renders a reference table listing *all* benchmarkable sorting (8) and string-matching (3) descriptors with best/average/worst/space/paradigm (`rows` in `ComplexityTab.jsx` combines both categories regardless of the active domain), plus a ComparePanel that runs only the current domain's benchmarkable algorithms side-by-side at n=100 (or text size 500) on the main thread via `measure`.
- **AI** (`AIAssistantTab`): user picks language (default Arabic), chats / quick-actions / recommend form / "Analyze results" (which inlines current benchmark numbers into the prompt). Every request POSTs `{messages}` to `VITE_AI_ENDPOINT || "/api/assistant"`; reply text is appended to the chat.

### Crash flow
Uncaught render errors bubble to `ErrorBoundary`, which shows a friendly screen with a reload-state button (`src/components/ErrorBoundary.jsx`).

## 9. Frontend Architecture

- **Single-root composition, no router.** `App.jsx` holds `domain` and `subTab`; the "route" is derived. Tab state persists across reloads.
- **Everything flows via props.** `App.jsx` composes per-domain control objects (`sortControls`, `vizControls`, `searchControls`, `historyControls`, `pseudoControls`) handed to `ConfigSidebar`; main content is switched inline with `{subTab === "x" && …}`.
- **Presentational + domain split.** Algorithm execution and benchmark logic live in `src/algorithms` and `src/core`; React components consume their outputs. The DOM/React modules never contain algorithm logic (checked: algorithm modules import only `core/execution`, `core/structures`, or plain code).
- **Theme system.** Design tokens are JS-first (`getPalette(theme)` inline styles) with a supporting CSS-variable layer for charts/global focus in `src/styles/index.css`. Toggling theme flips a `data-theme` attribute; `ThemeCtx` provides the current theme to components that need it.
- **Custom hooks** centralize cross-cutting concerns: persistence, playback, benchmark orchestration, history.
- **Degenerate/defensive rendering** is a convention: registry helpers return stubs or `null` for stale ids (`getAlgorithmSafe`, `getAlgorithmForDisplay`), and `usePersistentState` never throws on corrupt storage. E2E tests explicitly cover "stale algorithm id in localStorage" scenarios (`cypress/e2e/app.cy.js`).
- **No CSS-in-JS library** — styling is inline `style` objects + a handful of global classes (`.surface-card`, `.glass-*`, `.icon-btn`, `.panel-in`, `.popover-in`).

## 10. Backend Architecture

There is effectively **one serverless function**:

- **`api/assistant.js`** — default-exported `handler(req, res)` (Vercel Node runtime style).
  - Optional CORS: only when `ALLOWED_ORIGIN` env is set → reflects exactly that origin (no `*`, no credentials header), `Vary: Origin`.
  - `OPTIONS` always → 204 (CORS headers are attached only when `ALLOWED_ORIGIN` is configured); any non-POST → 405.
  - Shared rate limit when configured: with `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` set, a sliding-window 15 requests / 60 s per client IP limit runs through Upstash Redis (`@upstash/ratelimit` + `@upstash/redis`, dynamically imported), so the window is shared across serverless instances. Without those vars the endpoint uses the per-instance in-memory limiter (`x-forwarded-for` first value or socket address, map cleanup when > 10 000 buckets) with identical limits, and if Upstash errors mid-flight it degrades to that limiter rather than failing.
  - Server-owned system prompt: the handler injects its own `SYSTEM_PROMPT` as the *only* system-role message; client-supplied `"system"` messages are demoted to `"user"`, so a caller can never override the model's instructions.
  - Prompt-injection screening: user-originated content is checked against lightweight English + Arabic patterns (`ignore … instructions`, `you are now`, `reveal your system prompt`, `jailbreak`, `developer mode`, …) and rejected with a clear 400 before reaching Groq (`looksLikePromptInjection`). App-authored messages (the demoted client system prompts) are not scanned, since their defensive wording contains example phrases the patterns would flag.
  - Body must be JSON with `messages[]` (1–20), each `{ role ∈ {system,user,assistant}, content ≤ 8000 chars }`; role sanitized to `user` if invalid.
  - Requires `GROQ_API_KEY`; otherwise responds 501 *without* echoing key material (tested in `api/assistant.test.js`).
  - Calls Groq `https://api.groq.com/openai/v1/chat/completions` with `model: "llama-3.3-70b-versatile"`, `max_tokens: 1000`; maps upstream 429 → 429, other failures → 502 with the upstream error message.
- There is **no persistent backend, no database, no user accounts**. The "backend" responsibilities that exist (AI proxy) are documented in `README.md` ("Requests are proxied through a serverless function — no API key ships to the browser").
- Local development of the endpoint: `vercel dev` executes `api/` functions locally (`README.md`).

"Schema" notes:

No migrations exist (nothing server-side); the only non-localStorage configuration lives in environment variables (§18).

## 12. API Documentation

### `POST /api/assistant` (serverless; also reachable via `VITE_AI_ENDPOINT`)
Implementation: `api/assistant.js`. Client caller: `callAssistant()` in `src/tabs/AIAssistantTab.jsx`.

- **Purpose**: Proxy chat-completion requests to Groq so the model API key stays server-side.
- **HTTP method**: `POST` only (GET → 405; `OPTIONS` always → 204, with CORS headers attached when `ALLOWED_ORIGIN` is configured).
- **Authentication**: none from the client. The server authenticates to Groq with `Authorization: Bearer $GROQ_API_KEY` (read from server env). Unconfigured deployments return 501.
- **Request body** (JSON):
  ```json
  {
    "messages": [
      { "role": "system", "content": "…" },
      { "role": "user",   "content": "…" }
    ]
  }
  ```
  Constraints: 1–20 messages (`MAX_MESSAGES = 20`); every message needs a string `content` (else 400); content truncated to 8000 chars; roles limited to `system`/`user`/`assistant` (else coerced to `user`); oversized arrays → 413. The server prepends its own authoritative system prompt as the *only* `system` message — client-supplied `system` messages are demoted to `user` (§10, §22).
- **Response** (success, 200):
  ```json
  { "content": "<model reply text>" }
  ```
- **Errors**:
  - `400 { error: "messages[] is required" }` / `{ error: "Each message needs a string content field" }` / `{ error: "Invalid JSON body" }` / `{ error: "Message contains text that looks like a prompt-injection attempt and was not sent to the model." }` (screened user content — §22)
  - `405 { error: "Method not allowed" }`
  - `413 { error: "Too many messages (max 20)" }`
  - `429 { error: "Too many requests — please wait a minute and try again." }` when the endpoint's own rate limit trips; an upstream Groq 429 is also forwarded as status 429, but with the provider's own error text.
  - `501 { error: "The AI assistant is not configured…" }` (no `GROQ_API_KEY`)
  - `502 { error: … }` (upstream failures / malformed response / network error)
- **Rate limiting**: sliding-window 15 req/60 s per client IP via Upstash Redis when `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are set (shared across instances); otherwise the per-instance in-memory limiter with identical limits, also used as fallback when Upstash is unreachable (§10).
- **CORS**: no headers unless `ALLOWED_ORIGIN` is set, in which case exactly that single origin is allowed, `Vary: Origin`, no `Access-Control-Allow-Credentials`.

There are **no other API endpoints** in the repository. All other application behavior is client-side.

## 14. Core Business Logic

This is an *educational benchmarking/debugging* app; the "business logic" is the algorithm catalogue and the measurement methodology.

### Benchmark methodology (`src/core/benchmark/engine.js`, `jobs.js`)
- Inputs generated once per (scenario, size) and **shared** across algorithms → paired comparison on identical data (docstring in `engine.js`; regression-tested in `engine.test.js`).
- `measure()` runs `warmup` (default 1) unmeasured iterations for JIT warm-up; the timed region excludes `setup()`; each repeat times only `fn(...args)`; the **median** of the repeats is reported to resist outliers. The engine's own fallbacks are `warmup ?? 1` / `repeats ?? 3` (`runBenchmarkJob`), but the spec layer always materializes `DEFAULT_WARMUP = 1` / `DEFAULT_REPEATS = 5` (`jobs.js`), so real runs use 1 warmup × 5 repeats. `round4` normalizes floats; basic operations (`comparisons`, `matches`) come from the first measured invocation's output.
- Measurement points: `{ n, time, comparisons }` (+ `matches` when a scenario sets `collect: "matches"`).
- Hard limits (`LIMITS` in `src/core/benchmark/jobs.js`):
  - **Input-size cap** — every single input (generated arrays, custom arrays and uploaded text alike) is capped at 200 000 elements/chars via `maxSizePerPoint`, enforced through `rejectOverLimit`.
  - **Points cap** — a run may not exceed 24 benchmark points (`maxPointsPerRun`).
  - **Sync-fallback budget** — inline execution is only used when every input size is ≤ 5 000 (`maxSyncFallbackSize`, checked by `isWithinSyncBudget`).
  - **Dead constants** — `maxCustomArrayLength` (100 000) and `maxFileTextLength` (200 000) are defined but **not referenced by any validation path**; custom-array and file-text lengths are validated against `maxSizePerPoint` like everything else.
- Cancellation & failure taxonomy (`runner.js`): `BenchmarkCancelledError` (AbortSignal), `BenchmarkTimeoutError` (120 s watchdog), `BenchmarkBudgetError` (worker unavailable + oversized for sync). Errors are user-readable via `describeBenchmarkError` (`useBenchmarks.js`).

### Algorithm semantics (spot checks against real code)
- Sorts return `{ sorted, comparisons }` and never mutate input (they defensively copy: `const a = [...arr]` in `insertionSort.js`, `bubbleSort.js`, `selectionSort.js`, `mergeSort.js`, `quickSort.js`; same convention in heap/counting/radix, verified by tests).
- Counting Sort returns `comparisons: 0` by design (non-comparison); Radix Sort likewise reports 0 comparisons (descriptor `radix-sort` maps `run` to `radixSortEvents`).
- String matchers return `{ matches, comparisons }` (all *occurrences*, including overlapping, consistent across brute-force/horspool/kmp — tested in `contracts.test.js`).
- Binary Search `debug` sorts a defensive copy and picks a middle-element target by default or a caller-supplied target; used for found & not-found walkthroughs.
- Graph model (`src/algorithms/graphs/graph.js`) is an adjacency object; neighbor entries are either plain strings (weight 1) or `[to, weight]`. Editor operations treat edges as **undirected** (both directions written/removed), reject self-loops, duplicate edges, non-finite weights, and validate node ids — all with descriptive thrown errors surfaced in the UI as notices.
- Dijkstra rejects any negative weight with a message naming the edge (pre-scan, `dijkstra.js`); Bellman-Ford allows negative weights, early-stops when a pass makes no changes, and runs an extra pass to detect *reachable* negative cycles (`bellmanFord.js`); Floyd-Warshall detects negative cycles on the matrix diagonal (`floydWarshall.js`); Prim/Kruskal produce a minimum spanning **forest** with `treeCount`/`connected` when the graph is disconnected (`prim.js`, `kruskal.js` — default example graph is intentionally disconnected for Prim, per `prim.test.js`).
- Debug snapshots keep `activeLine` within `codeLines` bounds and end with a terminal log (asserted by `contracts.test.js` for every debuggable algorithm).

### Persistence & history
- History capped at 20 (`MAX_HISTORY`, `useRunHistory.js`); comparison capped at 4 and restricted to same-kind runs (`HistoryTab.jsx`).

## 16. Data Flow

### Debug/visualization data flow
```
user clicks GENERATE
  → DebuggerTab/GraphDebugger/App.startViz()
  → descriptor.debug(input) | descriptor.steps(input)
  → [snapshot] (sorting/searching)          → usePlayback(index)
  → events (modern sorts & graph algos)      → step state → render
       → projectSortingEvents / projectPathfindingEvents /
         projectMstEvents / projectMatrixEvents
       → [snapshot]
render layers per domain:
  DebuggerTab → bars / string grids / LPS / shift tables / vars /
                memory / call stack / code lines
  GraphDebugger → GraphSVG (colors, edge states, distance badges) /
                  queue|stack|frontier|distances panels / MatrixView
  VisualizerTab → bars + boundary/sortedFrom markers
```

### Benchmark data flow
```
ConfigSidebar (settings) → spec {kind, algoIds, types|scenarios, sizes,
  pattern, customArrayStr, metric, inputMode, text, …}
  → useBenchmarks.validateSpec (errors → BenchmarkError banner)
  → runner.runBenchmark (worker | sync fallback)
  → worker → jobs.materializeSpec → engine.runBenchmarkJob
  → results {algoId: {type|scenario: [{n, time, comparisons, matches?}]}}
  → envelope persisted (results:sort / results:search) + pushed to history
  → charts (line avg vs n, bar first type), tables, report, AI analysis
  → exportCSV / exportXLSX / PNG
```

### AI data flow
```
AIAssistantTab (lang, messages, results envelope)
  → callAssistant POST {messages: [systemPrompt(lang), …last 10]}
  → /api/assistant (rate limit → validate → GROQ_API_KEY → fetch Groq)
  → {content} → appended to chat state
```

### State-persistence flow
Any setting change goes through `usePersistentState`, which serializes the next value to `localStorage["algo-app:v1:"+key]` inside the state updater, swallowing storage errors.

## 22. Security Analysis

### Mechanisms already implemented
- **Secret isolation**: `GROQ_API_KEY` only in `api/assistant.js` server env; README/INSTALL_NOTES warn explicitly against `VITE_`-prefixing (would leak into the public bundle). Structural test asserts no key-shaped output (`api/assistant.test.js`).
- **Shared rate limiting**: sliding-window 15 req/60 s per client IP on the AI endpoint, via Upstash Redis (`@upstash/ratelimit` + `@upstash/redis`) when `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are set — the window is shared across serverless instances. Without them (or if Upstash is unreachable) it falls back to the per-instance in-memory limiter with identical limits (`api/assistant.js`).
- **Server-owned system prompt**: the endpoint injects the *only* system message; client-supplied `system` messages are demoted to `user`, so a caller can never replace or override the model's instructions (`SYSTEM_PROMPT` in `api/assistant.js`).
- **Prompt-injection screening**: user-originated content is checked against lightweight English + Arabic jailbreak patterns (`ignore … instructions`, `you are now`, `reveal your system prompt`, `jailbreak`, `developer mode`, …) and rejected with a clear 400 before reaching Groq — never silently sanitized (`looksLikePromptInjection`).
- **Content-Security-Policy (production builds)**: `cspMetaPlugin` in `vite.config.js` injects a strict CSP `<meta>` into the built `index.html` — `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self' https:; object-src 'none'; base-uri 'self'; form-action 'self'`. Nothing remote is allowlisted beyond `https:` (for an optional cross-origin `VITE_AI_ENDPOINT`); the app loads no remote scripts, styles, fonts, or images. Injection happens at build time only, so dev/HMR (Vite's inline react-refresh preamble) is unaffected.
- **AI-generated labeling**: the AI tab shows a permanent, visible notice (AR/EN) above the chat input that responses are AI-generated and may be inaccurate (`src/tabs/AIAssistantTab.jsx`).
- **Payload validation & caps**: method whitelist, JSON parse guard, `messages` 1–20, role whitelist, content length cap 8000, `max_tokens: 1000` upstream (`api/assistant.js`).
- **CORS posture**: no headers by default (same-origin); when `ALLOWED_ORIGIN` is set, exactly one explicit origin, `Vary: Origin`, and **no** `Access-Control-Allow-Credentials` (asserted by test).
- **Error hygiene**: unconfigured-key response is generic ("not configured…"); upstream error text is relayed but the API key itself is never included in responses or logs.
- **Input hardening on benchmarks**: hard limits on sizes/points and watchdog timeouts prevent browser DoS from absurd inputs; cancellable workers are terminated on abort (`src/core/benchmark/runner.js`, `jobs.js`).
- **Graph editor validation**: rejects self-loops, duplicate edges, non-finite weights, empty ids (`src/algorithms/graphs/graph.js`) — primarily correctness, secondarily UI-safety (no NaN/Infinity rendered into SVG).
- **Frontend resilience**: top-level `ErrorBoundary`; JSON-parsing of `localStorage` wrapped in try/catch (`usePersistentState.js`); safe registry lookups for stale ids.
- **Reduced attack surface**: one POST-only endpoint; no cookies/sessions; no third-party scripts in the app shell (now enforced by the production CSP).

### Potential vulnerabilities / weaknesses
- **Rate-limit identity is spoofable**: the limit keys on the client IP extracted from `x-forwarded-for` (first value) — an attacker can rotate that header unless the hosting platform sanitizes it. And without Upstash configured (or when Upstash is unreachable) the fallback limiter is per warm instance, so scaled-out deployments without Upstash multiply the effective quota.
- **No authentication on the AI proxy** — cost/abuse surface (mitigated only by the rate limit — shared when Upstash is configured — and the message/content caps).
- **Prompt injection is mitigated, not eliminated**: the server-owned prompt and English/Arabic pattern screening (400 on match) stop the common jailbreak phrasings, but the pattern list is deliberately lightweight — a full moderation/content-safety service remains a future improvement (§27), and there is no output-side filtering of model responses.
- **Error message leakage**: `502` responses relay `data?.error?.message` from the upstream provider; if Groq ever returned text containing sensitive configuration details it would be forwarded (currently unlikely).
- **CSP scope is limited to the built app**: the policy is injected into production builds only — dev mode and the separate `landing/` page are exempt, and `landing/index.html` deliberately loads remote Google Fonts/FontAwesome and a CDN video with no CSP of its own (an accepted limitation of that standalone page).
- **`localStorage` persistence** stores benchmark data and history unencrypted — it is same-origin readable by any script on the origin and persists results that can be large (quotas may be hit silently; writes are best-effort with errors swallowed).
- **XSS surface** is low but non-zero where model text or user text is rendered: `AIAssistantTab` builds JSX from strings (React escapes by default) and splits on `**` for bold only; debug/benchmark panels render numbers/strings via JSX too. File uploads are read as text and capped, never executed.
- No dependency audit artifacts: the snapshot has no `npm audit` state; `xlsx` is a single-purpose export lib loaded dynamically.

## 23. Error Handling

- **UI crash containment**: `ErrorBoundary` (`src/components/ErrorBoundary.jsx`) catches render errors, logs them, and offers "RELOAD APP STATE".
- **Benchmark failures are first-class**: `validateSpec` returns a human string (e.g. "exceeds the maximum of …", "This run would execute N benchmark points…"); `runBenchmark` throws typed errors that `describeBenchmarkError` (`src/hooks/useBenchmarks.js`) converts into messages: cancellation → silently ignored (UI returns to idle); timeout → "Benchmark stopped after Xs — likely too much work…"; budget → guidance to reduce sizes. Rendered via `BenchmarkError` (`[role="alert"]`) in `ConfigSidebar`.
- **Worker degradation**: if worker construction fails *and* the job fits the sync budget, the benchmark runs inline; otherwise a clear error is raised rather than silently hanging (`runner.js`).
- **Debounced/guarded inputs**: debugger truncates oversized arrays/text/patterns with visible `⚠` notices (`DebuggerTab.jsx` — max 64/2000/100); visualizer steps recomputed only for algorithms exposing `steps` (`startViz` guards `typeof d.steps === "function"`).
- **Graph editor errors**: every pure graph mutation throws descriptive errors (`graph.js`); `GraphDebugger.applyMutation`/`generate` catch and show notices (e.g. "Dijkstra does not support negative weights", "Self-loops are not supported", "Node X already exists"). Negative-cycle and MST-forest outcomes are shown as success/alert banners.
- **Persistence errors** swallowed (try/catch in `read`/`setItem` of `usePersistentState.js`) so corrupt storage never crashes the app.
- **Export errors**: `exportXLSX` catches SheetJS failures and falls back to CSV; PNG export silently no-ops when no `<svg>` is found.
- **AI errors**: non-OK responses and thrown fetch errors are rendered in-chat as `❌ Error: …` (`AIAssistantTab.send`); the server returns structured `{error}` bodies.
- **Empty states** guide the user (e.g. `Empty` component "Configure & Run Sorting Benchmark", Report's "Run a benchmark first…", Debugger's "Select an algorithm and click Generate").

## 26. Limitations

- **Single-user, in-browser only**: no accounts, sync, server persistence, or multi-device history (localStorage is per-browser).
- **Rate limiting is shared only when configured**: without `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` (or if Upstash is unreachable) the AI endpoint falls back to a per-instance in-memory limiter, which does not bound abuse across scaled-out instances. The rate-limit key is the client IP as seen in `x-forwarded-for`, which callers can spoof if the platform does not sanitize it (§22).
- **Visualizer supports arrays only for sorting**; searching/string-matching and graph domains have no "visualizer" sub-tab (only the step debugger).
- **Charts are simple static SVG**: no zooming/tooltips/interactivity beyond fullscreen; bar chart plots only the first scenario/type.
- **Timing benchmarks are in-browser** — absolute ms values are machine-dependent; the code and the report UI explicitly frame results as single-machine observations (see `ScalingAssessment` caveat text).
- **Tooling gaps**: no TypeScript, linter, formatter, or CI config in the repo; code quality relies on tests and conventions (see §25/§27).
- **Front-end size**: `App.jsx`/`GraphDebugger.jsx`/`AIAssistantTab.jsx` are large monoliths; settings are props-drilled through control objects, which grows with each feature.
- **Minimal documentation of the "event vocabulary"** beyond docstrings and tests (no standalone architecture doc besides README).

## 29. Executive Summary

**Algo App** is a self-contained, dependency-light React 18 + Vite 5 web application for studying classic algorithms empirically and interactively: it benchmarks 8 sorting algorithms and 3 string-matching algorithms against controlled inputs inside a Web Worker (median-of-repeats timings, comparison counts, shared inputs for fairness), visualizes 6 sorts frame-by-frame, and steps through every sorting, string-matching, binary-search and graph algorithm (DFS, BFS, Dijkstra, Bellman-Ford, Floyd-Warshall, Prim, Kruskal) in a "memory debugger" that renders source lines, variables, memory, stacks/queues/heaps and, for graphs, a fully editable SVG playground with MST/shortest-path state.

Architecturally it stands out for a **single canonical algorithm descriptor** (`src/algorithms/registry.js`) and a **pure-execution/event → projector → snapshot** seam (`src/core/execution/events.js` + the four projector modules) that keeps algorithm code UI-free and fully deterministic — properties the extensive Vitest suite locks in with one-event→one-step and determinism assertions. The benchmark core (`src/core/benchmark/`) is a miniature framework with spec validation, hard input limits, cancellation, timeouts and graceful fallback. The only backend is one Vercel-style serverless function (`api/assistant.js`) that proxies the optional Arabic/English AI tutor to Groq with the API key held server-side, per-IP rate limiting (shared across instances via Upstash when configured), prompt-injection screening, and single-origin CORS.

The project is in a healthy, clearly "near completion" state for its course purpose: 19 descriptor-registered algorithms are implemented, 21 test files (19 Vitest unit/component suites + 2 Cypress E2E specs) are present and the unit suite is green (348/348 tests), and the working tree carries a batch of verified fixes on top of HEAD `4ed19456` — a working `make start`, fully populated search-table columns, removed dead/duplicate files, a build-time CSP, shared Upstash rate limiting, and prompt-injection hardening (§22). Remaining rough edges are minor and well localized: unreachable FR/DE AI strings, a stray `.env.example` header, no lint/CI config, and an unrelated tracked `landing/` marketing page (assets repaired, CDN dependencies documented) whose E2E spec is deliberately excluded by default. No database or authentication exists, which is consistent with a client-side educational tool; the security posture is now a production CSP, a server-owned system prompt with prompt-injection screening, permanent AI-generated labeling, and shared rate limiting when Upstash is configured (per-instance fallback otherwise).

**Bottom line**: a polished, test-covered algorithm teaching tool whose central idea — "describe an algorithm once; let benchmarking, visualization, debugging and reporting derive from it" — is executed consistently, and which can grow new algorithms, new domains, or even a real backend with minimal structural change.
